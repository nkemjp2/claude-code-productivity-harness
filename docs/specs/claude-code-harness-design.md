# Claude Code Quality Harness — Design

**Author:** Nkem Joseph-Palmer
**Status:** Draft for implementation
**Scope:** Stack-agnostic control system for agentic coding sessions, instantiated through Claude Code hooks, subagents, skills and repo conventions.

> **Editorial note.** This file is the specification as supplied, committed
> unchanged. Where a Phase 0 finding supersedes a passage, a blockquote names
> the ADR. The original text is never edited, so a reader can see both what was
> specified and what was decided — ADRs are append-only and this file is their
> subject, not their competitor.

---

## 1. Problem statement

Post-hoc diff reviewers detect defects after the agent has already committed to a plan. They cannot address the two upstream causes of technical debt and misalignment:

1. The plan was wrong before a line was written (ambiguous contract, missing context, wrong blast radius).
2. Nothing structurally forces the loop closed (the agent declares completion; nothing independently verifies it).

This harness is a **control** layer rather than a detection layer. Diff review remains in the stack as a backstop, not as the primary quality mechanism.

### Objectives

| ID | Objective | Primary measure |
|----|-----------|-----------------|
| O1 | Reduce escaped defects per merged change | Post-merge defects attributed to agent-authored commits |
| O2 | Eliminate premature completion | Tasks reaching `Stop` without a passing evidence bundle |
| O3 | Raise assertion integrity | Mutation score on changed files |
| O4 | Keep context correct and current | Rule-load coverage; rework rate |
| O5 | Make agent work auditable | Percentage of merged changes with complete evidence bundle and criterion trace |
| O6 | Bound cost and human attention | Tokens and interventions per completed task |

### Non-objectives

- Replacing human review on protected paths.
- Removing existing diff-review tooling.
- Achieving full autonomy. The target is high-yield supervised work, not unattended work.

---

## 2. Design principles

| # | Principle | Consequence |
|---|-----------|-------------|
| P1 | Control, not detection | Gates block; they do not annotate. |
| P2 | Deterministic first | Model-based judgement only where determinism is impossible. |
| P3 | Fail closed | An unenforceable rule is not a rule. A misconfigured gate must be detectable. |
| P4 | Evidence, not assertion | "Done" is a machine predicate over artefacts on disk. |
| P5 | Memory only if enforced | If no gate reads a rule, it does not go in the instruction corpus. |
| P6 | Tight loops beat big loops | Feedback at the edit is worth more than feedback at CI. |
| P7 | Legibility is upstream of everything | Repo navigability sets the ceiling on output quality. |
| P8 | The harness is a product | Versioned, tested, measured, and subject to its own review cadence. |

---

## 3. Architecture

Sixteen layers across four bands. Foundations raise the ceiling; the pipeline governs each task; the loop makes the system improve; governance keeps the harness honest.

```
FOUNDATIONS   F1 Repo legibility        F2 Gate credibility       F3 Containment
                     |                          |                         |
PIPELINE      L0 Work contract -> L1 Context -> L2 Memory -> L3 Inner-loop gates
                  -> L4 Completion gates -> L5 Assertion integrity
                  -> L6 Non-functional gates -> L7 Traceability
                     |
LOOP          M1 Observability -> M2 Classification -> M3 Codification
                     |
GOVERNANCE    G1 Harness versioning  G2 Rule hygiene  G3 Eval set
              G4 Escalation  G5 Budgets & recovery  G6 Effort routing
```

## 4. Foundations

### F1 — Repo legibility

The largest single determinant of agent output quality, and entirely under your control.

**Requirements**

- R-F1.1 One canonical command each for build, test, lint, typecheck, run, and migrate. Declared in a machine-readable manifest at repo root that hook scripts read, so gate definitions never hardcode commands.
- R-F1.2 Selective test execution. The harness must be able to run only tests affected by the current diff. If the full suite is the only option and it is slow, there is no inner loop.
- R-F1.3 Typed module boundaries, colocated tests, predictable naming.
- R-F1.4 A generated repo map (module index, public exports, ownership, layer assignment) regenerated by a hook when structure changes, and referenced from the instruction corpus rather than pasted into it.
- R-F1.5 Executable documentation. Any code sample in docs is compiled or run in CI. Documentation that lies is worse than absent documentation, because the agent believes it.
- R-F1.6 No hidden setup. A fresh clone plus one bootstrap command reaches a green build.

**Toolchain adapter.** All gates invoke abstract verbs (`typecheck`, `test:affected`, `mutate:diff`, `lint:diff`, `arch:check`, `perf:budget`, `sast`, `deps:check`) resolved through the manifest. This keeps the harness portable across repos and stacks.

### F2 — Gate credibility

A harness built on gates dies the moment the gates are noisy. Flaky signals teach both you and the agent to route around them.

**Requirements**

- R-F2.1 Pinned toolchain and containerised dev environment, so the agent's run and CI's run are the same run.
- R-F2.2 Determinism in tests: seeded randomness, frozen clock, no network in unit tests, no shared mutable fixtures.
- R-F2.3 Automatic flake detection with quarantine. Quarantined tests are tracked as debt with an owner and expiry, never silently deleted.
- R-F2.4 **Fail-closed discipline.** Claude Code treats exit code 1 as a non-blocking error and proceeds; only exit code 2 blocks on events that can block. A mistyped script path leaves a gate silently disabled, surfacing only as a transcript notice on first run. Therefore:
  - Every gate script is unit tested by piping sample event JSON to stdin and asserting the exit code.
  - A **canary suite** runs in CI: for each gate, stage a deliberate violation and assert the gate blocks. A gate that stops firing is a build failure.
  - Never suppress a validator's failure (no trailing `; true`). Distinguish "clean" from "the parser could not read the file the agent just wrote" — the second is exactly the signal you want surfaced.
  - Hard allow/deny lives in the permission system, not in a hook. The hook `if` filter is documented as best-effort, and Claude Code runs the hook regardless when it cannot determine what a Bash command expands to.
- R-F2.5 Gate retirement rule: any gate that fires falsely and is not fixed within one review cycle is removed. An untrusted gate launders failure.
- R-F2.6 Hooks run without a controlling terminal. No gate may be interactive. User-visible messages use `systemMessage`; notifications use `terminalSequence` (allowlisted OSC sequences only).

### F3 — Containment

Two distinct concerns: what the agent may reach (trust boundary) and what it may damage (blast radius).

**Trust boundary.** Issue text, PR comments, dependency READMEs, fetched web pages and MCP tool output are all untrusted input reaching an actor with write access to the repo and a shell.

- R-F3.1 Context sources are classified `trusted` (repo instruction corpus, ADRs, task contract) or `untrusted` (everything fetched or quoted). Untrusted text carries no instruction authority; the injection wrapper states this explicitly when such content enters context.
- R-F3.2 Secret scanning as a `PreToolUse` gate on write tools, plus a pre-push gate. Agents paste credentials into fixtures.
- R-F3.3 Scoped, short-lived credentials only. No production tokens in the agent environment. Note that hook processes inherit the parent environment.
- R-F3.4 Network egress allowlist for the session.
- R-F3.5 MCP tools appear as ordinary tools named `mcp__<server>__<tool>` and are matchable like any other tool. Every write-capable MCP tool is gated; the matcher must end in `.*` after the server prefix to match a whole server.

**Blast radius.**

- R-F3.6 One worktree per task. `WorktreeCreate` and `WorktreeRemove` hooks handle setup and teardown. Note that any non-zero exit from a `WorktreeCreate` hook aborts creation, and its stdout is read as the worktree path, so it cannot return JSON.
- R-F3.7 Protected path register requiring explicit human approval: migrations, infrastructure, CI config, lockfiles, auth and crypto code, generated artefacts, and the harness's own configuration (`.harness/manifest.yaml`, `.harness/policy.yaml`, `.claude/settings.json`). `.harness/tasks/**` is explicitly carved out of the protected register, because task artefacts are written during normal work.
- R-F3.8 Destructive command denial at the permission layer.
- R-F3.9 Clean abandon path. Any session must be discardable without residue.
- R-F3.10 `${CLAUDE_PROJECT_DIR}` stays at the session's project root even after entering a worktree; the `cwd` field in hook input follows the agent. Gate scripts must read `cwd` when they need the working directory.

## 5. Pipeline

### L0 — Work contract

Defect rate is a function of task size and spec ambiguity. Everything downstream is damage limitation if this layer is weak.

**Requirements**

- R-L0.1 Every task has a contract file at `.harness/tasks/<task-id>/contract.yaml` containing: intent, in-scope, explicitly out-of-scope, acceptance criteria with stable IDs, declared blast radius (paths the task may touch), and non-functional constraints that apply.
- R-L0.2 Acceptance criteria are written as executable statements. A criterion that cannot be expressed as a test is either decomposed or reclassified as a design note.
- R-L0.3 One vertical slice per session. Net diff soft cap (default 400 changed lines) beyond which a plan artefact and explicit approval are required.
- R-L0.4 Blast radius is enforced, not advisory: a `PreToolUse` gate denies writes outside declared paths, with the denial reason naming the contract. `.harness/tasks/<id>/plan.md` and `handoff.md` are implicitly in scope for the active task; `.harness/tasks/<id>/evidence/**` is **denied to the agent entirely** — see R-L4.4a.

This is INVEST plus a Definition of Done made machine-checkable rather than social.

### L1 — Context supply

Engineer the supply of context; do not stuff the window.

- R-L1.1 **Constitution.** `CLAUDE.md` holds only short, imperative rules that a gate enforces. Target under 200 lines.
- R-L1.2 **Path-scoped rules.** `.claude/rules/*.md` load lazily rather than as one monolith.
- R-L1.3 **Load verification.** The `InstructionsLoaded` event fires when a `CLAUDE.md` or `.claude/rules/*.md` file loads into context, at session start and on lazy load. Log every load. Most "it ignored the rule" incidents turn out to be "the rule was not in context," and this is the only way to tell the two apart.
- R-L1.4 **Decisions.** ADRs carry rationale. Without the why, the agent re-litigates settled decisions on every fresh context.
- R-L1.5 **Session priming.** A `SessionStart` hook injects branch, task ID, contract summary and applicable DoD through `hookSpecificOutput.additionalContext`. Write these as factual statements ("The deployment target is staging"), not as imperative system commands, which can trigger prompt-injection defences.
- R-L1.6 **Compaction handoff.** `PreCompact` can block compaction. Use it to require a written handoff artefact (current state, decisions taken, open questions, files touched, criteria satisfied) before context is lost. This converts silent amnesia into an inspectable file. `PostCompact` re-injects the handoff.
- R-L1.7 Hook output strings, including `additionalContext`, are capped at 10,000 characters; longer values are written to a file and replaced with a path and preview. Injectors must summarise, not dump.
- R-L1.8 Static conventions belong in the instruction corpus, not in a hook. Reserve `additionalContext` for genuinely dynamic state.

### L2 — Memory

Four tiers, each with a distinct lifecycle:

| Tier | Contents | Store | Lifecycle |
|------|----------|-------|-----------|
| Constitution | Enforced invariants | `CLAUDE.md` | Stable; changes are reviewed |
| Decisions | ADRs with rationale and consequences | `docs/adr/` | Append-only; superseded, never edited |
| Learned constraints | Rules generated from escaped defects | `.claude/rules/` | Each has a reason, a linked incident, and a review date |
| Working memory | Per-task handoff and plan artefacts | `.harness/tasks/<id>/` | Discarded on task close |

- R-L2.1 A memory only counts if a gate enforces it (P5). Unenforced text is deleted, not demoted.
- R-L2.2 Every learned constraint links to the incident that produced it and the gate that enforces it. A rule with no gate is a bug in the codification step (M3).
- R-L2.3 Rule expiry. Rules added in response to a single incident accumulate and consume context budget indefinitely unless reviewed.

### L3 — Inner-loop quality gates

The highest-yield layer per unit of effort.

- R-L3.1 **Per-edit validation.** `PostToolUse` on `Edit|Write` runs format plus typecheck on the edited file only. `PostToolUse` cannot undo the tool, but exit code 2 surfaces stderr to Claude, giving a compiler-grade signal on the very next turn while the edit is still in working context.
- R-L3.2 **Per-batch validation.** `PostToolBatch` fires after a batch of parallel tool calls resolves and before the next model call; exit 2 halts the agentic loop. Run affected tests and diff-scoped lint here.
- R-L3.3 **Strictness as code.** Strict compiler configuration, ban on suppression comments in new code, ratcheting thresholds that can only move in one direction.
- R-L3.4 **Architecture fitness functions.** Layering and dependency-direction rules fail the gate rather than generate a review comment.
- R-L3.5 **Latency management.** Hooks run on every matching tool call. Use the `if` field (permission-rule syntax such as `Edit(*.ts)` or `Bash(git *)`) to avoid spawning processes needlessly, and `async` / `asyncRewake` for checks that are slow but not turn-blocking. Default timeouts are 600s for command, HTTP and MCP-tool hooks; 30s for prompt hooks; 60s for agent hooks. `SessionEnd` hooks share a 1.5s budget by default.
- R-L3.6 CI remains the backstop only. Feedback arriving minutes later never reaches the agent.

### L4 — Completion gates

Directly addresses incomplete work and premature victory declaration.

- R-L4.1 **Plan-first.** `PreToolUse` on `Edit|Write` denies the call when no plan artefact exists for the current task, returning `permissionDecision: "deny"` with a reason naming the missing artefact.
- R-L4.2 **Definition-of-done gate.** A `Stop` hook exits 2 when the evidence bundle is incomplete, which prevents Claude from stopping and continues the conversation with your stderr as the reason. This is the single highest-yield gate in the system.
- R-L4.3 **Task-level gate.** `TaskCompleted` exit 2 prevents a task being marked complete. `TaskCreated` exit 2 rolls back task creation, usable to reject tasks with no contract.
- R-L4.4a **Evidence is written by the runner, never by the agent.** Captured outputs are produced by the runner invoking manifest verbs and writing results directly; the agent has no write access to `evidence/`. An agent-authored evidence bundle is an attestation, which collapses P4 back into the assertion it was meant to replace.
- R-L4.4 **Evidence bundle, not claims.** The gate reads `.harness/tasks/<id>/evidence/` and requires:
  - captured typecheck output (clean),
  - captured affected-test output (green) with the command and commit SHA,
  - captured red-green pair for each behavioural change,
  - diff stat within declared blast radius,
  - criteria checklist mapping every criterion ID to at least one named test,
  - a mutation report for changed files meeting the ratchet, **fresh as of the current commit**; the `Stop` gate verifies freshness and never triggers a run, because a `Stop` gate may re-fire up to the retry ceiling and mutation runs are minutes long. Mutation executes at `TaskCompleted` or pre-push,
  - non-functional gate results where applicable.
- R-L4.5 **Loop safety.** A `Stop` gate that always blocks produces an expensive grind. Enforce a per-task retry counter in the bundle; on exceeding it, return `continue: false` with a `stopReason` and escalate (G4). The `Stop` payload also exposes a re-entrancy indicator — verify its exact field name against the current hooks reference before relying on it.

  > **Settled by the Phase 0 audit.** `stop_hook_active` is present in client 2.1.247, as is `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`. See `docs/event-map.verified.md`.

- R-L4.6 On `Stop` and `SubagentStop`, read `last_assistant_message` rather than the transcript file, which is written asynchronously and may lag the current turn.

### L5 — Assertion integrity

The layer nothing else in your stack covers. A bad assertion looks exactly like a test, which is why diff reviewers are weak here.

- R-L5.1 **Mutation testing on the diff**, with a ratcheted score. This is the only objective measure of assertion strength. Coverage is a floor, not a signal.
- R-L5.2 **Separation of duties.** A test-author subagent receives the contract and the public interface, never the implementation. The implementer subagent does not author its own tests. Subagents carry hooks in frontmatter and run with separate context; a `Stop` hook declared in a subagent is converted to `SubagentStop`.
- R-L5.3 **Red-green evidence.** The failing output from before the fix must be captured. A test that never failed proves nothing.
- R-L5.4 **Test-tampering gate, ordering-based.** `PreToolUse` with `if: "Edit(**/*.test.*)"` denies an edit to a test file **after the first implementation edit in the same task**, unless an override token is present in the contract. A same-task prohibition would forbid red-green outright, since R-L5.3 requires the test to be authored in that task; ordering is what distinguishes writing a test from retrofitting one. This closes "make it pass by changing the test."
- R-L5.5 Property-based tests wherever an invariant exists. Snapshot tests are the largest single source of false confidence and are gated to an allowlist.
- R-L5.6 Assertion-density check on new test files: a test body with no assertion fails the gate.

### L6 — Non-functional gates

Agents optimise for the visible objective. Everything unmeasured regresses.

- R-L6.1 Performance budgets and artefact size, evaluated on the diff.
- R-L6.2 Static application security testing and dependency vulnerability scanning.
- R-L6.3 Dependency governance: allowlist, licence check, and an explicit gate on any new direct dependency. Agents add packages casually.
- R-L6.4 Public API and schema contract checks, so breaking changes fail rather than surprise.
- R-L6.5 Accessibility and internationalisation checks where the surface warrants them.
- R-L6.6 Data-handling checks where regulated data is in scope: retention, logging of identifiers, encryption at boundaries.

### L7 — Traceability

- R-L7.1 Stable acceptance-criterion IDs appear in the contract, in test names, in the commit trailer, and in the pull request body.
- R-L7.2 Bidirectional check: every criterion maps to at least one test; every new test maps to a criterion or is flagged as orphaned.
- R-L7.3 Agent attribution in commit metadata (session ID, model, effort level, harness version).
- R-L7.3a **Defect-side linkage.** Attribution alone is half the substrate. Every defect record must carry the commit or commits it is attributed to, by convention enforced at defect close. Without both halves O1 is unmeasurable, and O1 is the primary objective.
- R-L7.4 Evidence bundles are archived on merge and addressable from the commit.

## 6. Loop

### M1 — Observability

- R-M1.1 Every gate invocation **in an initialised repo** appends one structured JSONL record. A dormant exit in a repo with no manifest logs nothing, because there is no initialised location to log to. Record fields: timestamp, `session_id`, `prompt_id`, `agent_id`/`agent_type` where present, task ID, event, tool, target path, gate ID, verdict, duration, harness version.
- R-M1.2 `prompt_id` matches the `prompt.id` attribute on Claude Code's OpenTelemetry events, so gate outcomes correlate with telemetry for a single prompt. Note that Claude Code removes `OTEL_*` exporter variables from subprocesses it spawns, so hook scripts must not assume they inherit the exporter configuration.
- R-M1.3 Metrics maintained on the event log:

| Metric | Definition | Use |
|--------|------------|-----|
| Gate-failure taxonomy | Count by gate ID and verdict | Which rule fires most; where context is failing |
| Rework rate | Files edited more than N times in one session | Thrash and ambiguity detector |
| Mutation score trend | Per changed-file score over time | Assertion integrity (O3) |
| Time-to-green | First edit to first fully green batch | Inner-loop health |
| Intervention count | Human escalations per completed task | Attention cost (O6) |
| Escape rate | Post-merge defects per agent-authored change | Primary outcome (O1) |
| Rule-load coverage | Rules loaded vs rules applicable | Context supply health (O4) |
| Cost per completed task | Tokens and wall clock | Economics (O6) |

- R-M1.4 Session replay: transcript path, event log and evidence bundle are jointly addressable by session ID.

### M2 — Classification

- R-M2.1 Every escaped defect is classified as one of: **missing context**, **missing gate**, **missing rule**, **ambiguous contract**, **model error**.
- R-M2.2 Classification cadence is weekly, treated as a retrospective with the agent as the subject. Frame the event log as the sprint artefact.

### M3 — Codification

- R-M3.1 Each classification maps to a mandated remedy:
  - missing context → new or corrected rule file plus a load-verification check
  - missing gate → new gate plus canary case
  - missing rule → rule plus the gate that enforces it
  - ambiguous contract → contract template change
  - model error → prompt or subagent change, and an eval-set case
- R-M3.2 If a lesson cannot be expressed as a gate, it does not enter the instruction corpus (P5).
- R-M3.3 Every codification adds a case to the eval set (G3) so the change is measured rather than assumed.

## 7. Governance

### G1 — Harness versioning and distribution

- R-G1.1 The harness lives in the repo. Cloud sessions on Claude Code on the web do not read local `~/.claude/settings.json`; hooks there come from the repo and from organisation-managed settings. Anything in user settings is invisible to other surfaces.
- R-G1.2 Scope allocation:

| Concern | Location |
|---------|----------|
| Shared, mandatory gates | `.claude/settings.json` (committed) |
| Personal preference | `~/.claude/settings.json` |
| Machine-local overrides | `.claude/settings.local.json` |
| Reusable across repos | Plugin `hooks/hooks.json` |
| Procedure-scoped | Skill frontmatter (persists for the session; `once: true` is honoured only here) |
| Role-scoped | Subagent frontmatter (runs only while that subagent runs) |

- R-G1.3 Harness version is stamped into every event record and commit trailer.
- R-G1.4 `disableAllHooks` and, at organisation scale, `allowManagedHooksOnly` are understood and deliberately configured rather than discovered.
- R-G1.5 Prefer exec form (`command` plus `args`) for any hook referencing a path placeholder, since each argument passes through without shell quoting.

### G2 — Rule hygiene

- R-G2.1 Lint the instruction corpus itself for contradictions, duplication and unbounded scope. Conflicting instructions across `CLAUDE.md`, rules files, skills and subagents are a common and hard-to-diagnose source of nondeterminism.
- R-G2.2 Context budget ceiling per session, with the corpus measured against it.
- R-G2.3 Quarterly rule review against expiry dates.

### G3 — Evaluation set

- R-G3.1 A fixed suite of representative tasks (a bug fix, a feature slice, a refactor, a migration, a task with a deliberately ambiguous contract) re-run whenever the harness changes.
- R-G3.2 **Two scoring tracks, only one of which gates.** Deterministic adversarial cases (injection attempt, vacuous test, silent contract break, blast-radius escape) are pass/fail and block a harness change outright. The O1–O6 measures are reported as directional trend only and never trigger a revert: an eval set of a handful of tasks has no statistical power to detect a change in escape rate, and gating on it reverts good changes on sampling noise.
- R-G3.3 Includes adversarial cases: prompt injection in an issue body, a test that passes vacuously, a change that silently breaks a public contract.

### G4 — Escalation and the human interface

The harness must decide when to spend your attention, which is the scarcest resource in the loop.

- R-G4.1 Written escalation triggers: contract ambiguity, protected-path change, gate failure after N attempts, security-relevant change, budget exceeded, unresolvable dependency conflict.
- R-G4.2 Equally explicit non-escalation criteria, so the agent does not stall on decisions already settled in an ADR.
- R-G4.3 Notification routing that reaches you when you are not watching. Use the `terminalSequence` field rather than writing to `/dev/tty`, which hooks cannot access. Note it is emitted only in interactive sessions.
- R-G4.4 Batch the review surface: one coherent change with a complete evidence bundle, not a stream of interruptions.
- R-G4.5 Escalations are logged and counted as a first-class metric, not treated as noise.

### G5 — Budgets, concurrency and recovery

- R-G5.1 Token and wall-clock budget per task, enforced by a gate rather than hoped for.
- R-G5.2 Thrash circuit breaker: same file edited more than N times, or the same test failing more than N times, halts and escalates. Without this, an L4 completion gate can become an expensive infinite grind.
- R-G5.3 Ownership boundaries when running parallel sessions, so two agents never hold the same files. `SubagentStart`, `SubagentStop` and `TeammateIdle` provide the coordination points; `TeammateIdle` exit 2 prevents a teammate going idle.
- R-G5.4 Commit granularity discipline so rollback is cheap and bisect remains useful.
- R-G5.5 Defined rollback procedure per protected-path category.

### G6 — Effort and cost routing

- R-G6.1 The effort level in force is exposed to hooks in the `effort` field and as `$CLAUDE_EFFORT`. Use it as a policy input.
- R-G6.2 `PreModelSwitch` can block a model switch; its matcher evaluates against the canonical target model name. Use it to enforce a floor for protected-path work and for adversarial review.
- R-G6.3 Routing policy: high effort for planning, contract interpretation and adversarial review; lower for mechanical refactors under strong gates.
- R-G6.4 A timed-out `PreModelSwitch` hook blocks the switch, whereas a timed-out `PreToolUse` command hook does **not** block the tool call. Do not rely on a stalled hook as a gate.

> **Struck by ADR-0003.** `PreModelSwitch` does not exist in client 2.1.247, so
> R-G6.2 and R-G6.4 are unbuildable and R-G6.3 loses its enforcement point.
> R-G6.1 survives: `CLAUDE_EFFORT` is confirmed present.

## 9. Repository layout

```
.claude/
  settings.json            # shared gates, committed
  rules/                   # path-scoped, lazily loaded rules
  agents/                  # implementer, test-author, adversarial-reviewer
  skills/                  # repeatable procedures
  hooks/
    lib/                   # shared helpers: event parsing, logging, manifest
    gates/                 # one script per gate, each independently testable
    tests/                 # gate unit tests + canary fixtures
CLAUDE.md                  # constitution
docs/adr/                  # decisions
.harness/
  manifest.yaml            # toolchain adapter: verbs -> commands
```

## 11. Implementation roadmap

| Phase | Delivers | Exit criterion |
|-------|----------|----------------|
| 0 | F1 legibility: manifest, one-command verbs, selective test runs, repo map | Affected-test run under the inner-loop latency target |
| 1 | F2 credibility: determinism, flake quarantine, gate harness with unit tests and canary suite | Canary suite green in CI |
| 2 | L4 completion: contract schema, evidence bundle, `Stop` and `TaskCompleted` gates, loop safety | No task closes without a complete bundle |
| 3 | L3 inner loop: per-edit typecheck, per-batch affected tests | Time-to-green measurably falls on the eval set |
| 4 | L5 assertion integrity: mutation ratchet, role separation, red-green, tamper gate | Mutation score reported and ratcheted on every change |
| 5 | F3 containment: worktrees, protected paths, secret scan, egress, MCP gating | Adversarial eval cases pass |
| 6 | L1/L2 context and memory: rules split, load telemetry, `PreCompact` handoff, tiering | Rule-load coverage instrumented |
| 7 | M1–M3 loop: event log, metrics, weekly classification and codification | First codified rule traced from incident to gate |
| 8 | L6 non-functional, L7 traceability | Criterion trace complete on every merge |
| 9 | G1–G6 governance: eval set, rule hygiene, escalation policy, budgets, effort routing | Harness changes gated by eval-set results |

Phases 2 and 3 deliver most of the observable improvement. Phases 0 and 1 make that improvement durable rather than illusory.

> **Note per ADR-0001.** This roadmap's numbering is strategic and is *not* the
> build's phase numbering. The work order defines its own Phases 0–8, and those
> govern scope. Referenced here by content, never by number.

## 12. Failure modes

| Failure mode | Countermeasure |
|--------------|----------------|
| Gate silently disabled by path typo | Canary suite (R-F2.4) |
| Exit code 1 used where 2 is required | Gate unit tests asserting exit codes |
| `Stop` gate causes infinite grind | Retry counter plus `continue: false` escalation (R-L4.5) |
| Ratchet gamed by trivially satisfying tests | Mutation score, not coverage; assertion-density check |
| Instruction corpus grows until it displaces working context | Budget ceiling, expiry dates, P5 |
| Contradictory rules across corpus levels | Corpus lint (R-G2.1) |
| Hook latency degrades the session | `if` filters, `async` / `asyncRewake`, per-gate duration in event log |
| Prompt injection via issue or fetched content | Trust classification, no instruction authority for untrusted text |
| Model-based gates reintroduce nondeterminism | Restricted to cases where determinism is impossible; outcomes logged and reviewed |
| Harness drift between local and cloud sessions | Repo-scoped settings (R-G1.1), version stamping |

## 13. Verification record

Verified against Claude Code documentation on 1 September 2026. Items 1–5 were flagged as open in the previous revision.

**Confirmed**

1. **`Stop` re-entrancy flag.** `stop_hook_active` is present in the `Stop` and `SubagentStop` input JSON and is `true` when a previous Stop hook already kept Claude running. Corroborated across multiple sources, including one quoting the official troubleshooting snippet; I did not read it directly in the reference page section, so treat the field name as high-confidence rather than certain.
2. **Platform-level loop cap.** `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` limits consecutive Stop-hook blocks before the session ends with a warning, default 8. The harness retry counter (R-L4.5) must escalate *below* this cap so the harness controls the exit rather than the platform. Reported by a third-party reference guide; confirm against the env-vars page before tuning.
3. **Subagent context isolation is real.** A subagent gets a fresh context window; the parent conversation is not included; the only inbound channel is the prompt string in the Agent tool call and the only outbound channel is the final response. Subagents cannot nest. This supports L5.2.
4. **Forks defeat that isolation.** A fork inherits the entire conversation, with system prompt and tools identical to the parent, and interactive sessions turn fork mode on by default from v2.1.232. A "test-author" reached by fork would see the implementation. L5.2 therefore cannot rest on invocation type alone — see the provenance countermeasure in the plugin moat spec.
5. **Cloud session behaviour.** Repo `CLAUDE.md`, `.claude/settings.json` hooks, `.claude/rules/`, `.claude/skills|agents|commands`, and `.mcp.json` all reach cloud sessions. Plugins declared in the repo's `.claude/settings.json` are installed at session start from the declared marketplace, and this requires network access to reach the marketplace source. User `~/.claude/` content and user-scope `enabledPlugins` do not reach cloud sessions.
6. **Cloud toolchain.** Anthropic-hosted sessions run Ubuntu 24.04 on x86_64 with Node 20/21/22, Python, `git`, `gh`, `jq`, `yq`, `ripgrep` pre-installed, with approximate ceilings of 4 vCPU, 16 GB RAM, 30 GB disk. Setup scripts must exit zero and finish within roughly five minutes or the session fails to start.

> **Phase 0 update.** Items 1 and 2 are now settled by direct inspection of
> client 2.1.247: both `stop_hook_active` and `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`
> are present. See `docs/event-map.verified.md`.

**Corrected from the previous revision**

- Cloud plugin support is stronger than assumed: repo-declared plugins do install in cloud sessions. The remaining constraint is network reachability of the marketplace, not the plugin mechanism.
- The `Stop` gate has a platform-level block cap, so an unbounded gate ends the session rather than grinding indefinitely. This changes the failure mode but does not remove the need for the harness's own counter.

**Still unverified**

- **Third-party tooling behaviour.** Mutation-testing runners, architecture linters, SAST tools, and how existing diff-review tooling interacts with a pre-merge gate. Verify against their own current documentation.
- **Disabling fork mode on current versions.** The environment variable to *enable* fork mode on earlier versions is documented; a supported way to disable it on v2.1.232 and later is not confirmed.
- **Private marketplace authentication in automated contexts.** Reported to require a host token in the environment for background updates. Not confirmed against the official marketplace documentation.
- **`plugin.json` field-level schema.** The directory conventions used in this design are corroborated, but individual manifest fields should be checked against the plugins reference before the first build.

  > **Checked in Phase 0, and the guess was wrong.** No `minimumClaudeCodeVersion`
  > field exists in client 2.1.247. See ADR-0007.

- **Threshold calibration.** Every numeric default here remains a starting parameter to be calibrated from your own event log, not an evidence-based recommendation.
- **Cost of full instantiation.** Phases 0–4 are likely to justify themselves; phases 5–9 should be adopted only where the eval set shows they pay.

**Standing rule.** Hook field names, defaults and event coverage are version-gated and change between releases. Pin a minimum Claude Code version in the plugin manifest, assert it at `SessionStart`, and re-run the canary suite after every upgrade.
